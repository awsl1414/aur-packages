# 注释规范

注释要**清晰、明了、高效、统一**。核心原则：只写代码无法自我表达的信息——删掉一句读者不损失任何东西，就该删掉。

## 规则

1. **必写 docstring**：模块、公共类/函数首行一句话概括「做什么」；复杂逻辑空行后展开「为什么/坑点」，不展开「是什么」。私有/自解释函数可省略或只写一行。
2. **解释「为什么」**：契约、不变量、外部库的非显然行为、设计取舍优先；显而易见的逻辑不注释。
3. **高信息密度**：一行能说清不写一段；要点式列表优于散文；用好的命名/类型/小函数替代注释。
4. **中文为主，标识符与术语保留原文**（`Linux.version`、`source_<arch>=()`），便于检索。
5. **内联注释短而紧贴代码**（半行内为宜）；超过一行的解释上移到 docstring。
6. **复杂流程用编号步骤**，按执行顺序排列。
7. **TODO/FIXME 带前缀与信息**：`# TODO(parser): 抽到公共常量`。
8. **日志 ≠ 注释**：日志面向运维，注释面向源码读者，互不替代。

## 风格细节

- docstring 用 `"""..."""`，首行不空行；列表项用 `-` 或数字，与正文空一行。
- 行内注释与代码空两格；独占行的注释 `#` 后空一格。
- 注释随代码同步更新——过时注释比没有注释更误导。

## 自检

`uv run ruff check .`；逐句问「删掉它读者会损失什么？」，答「无」就删。
